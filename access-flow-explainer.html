How signing in used to work, and how it works now

The short version: your data never moved â€” it's still the same four SharePoint lists. What changed is who's allowed to touch that data directly, and it's no longer "whichever person happens to be signed in."

i

Old way: every person's own Microsoft sign-in was used to open SharePoint directly, and a SharePoint list decided their role. New way: a person's sign-in only proves who they are â€” a separate small program (the "backend") checks their role and fetches the data on their behalf, using its own access, not theirs.

Before: the SharePoint-dependent way

What had to happen, in order, every time someone opened the tracker

OldDirect-to-SharePoint
  • Person signs in with their Microsoft account
  • If IT hadn't manually added them to the SharePoint site, they were stuck here a real, recurring bottleneck
  • Otherwise, the app used that person's own permissions to open SharePoint directly
  • It read a list inside SharePoint called "Access Control" to look up their role
  • If nobody had manually added a row for them there either, they were stuck again
  • From then on, the app read and wrote the 4 data lists using the person's own SharePoint access â€” meaning they could, in principle, also open SharePoint directly themselves and browse everything, including everyone else's access level
NewBackend-mediated
  • Person signs in with their Microsoft account — same first step
  • Signing in now only proves who they are. It grants no SharePoint access at all, to anyone
  • Their sign-in is handed to NeoEngage's own backend, which checks their email against a small Access table — not a SharePoint list
  • Adding someone is one row in that table — no SharePoint site membership required, ever
  • If they have a role, the backend reads/writes SharePoint using its own dedicated access, never the person's
  • Nobody signed into the tracker can open SharePoint directly, or see anyone else's access level — the backend only ever hands back that one person's own role

Side by side

What actually changed, point by point

AspectOld wayNew way
Who touches SharePoint? Every signed-in person, using their own Microsoft permissions Only the app's own backend, using access nobody else holds
Where's "who can do what"? A list inside SharePoint (Access Control) A separate Access table in Azure, outside SharePoint entirely
Granting someone access Manually add them to the SharePoint site, and manually add a row to the Access Control list Add one row to the Access table
Today: done by hand in Azure · Soon: a button in the app
Can a user see others' access? Yes — technically reachable via SharePoint itself No — the backend only ever returns a person's own role
How many access levels? 3 — Admin, Regional Admin, Regional Viewer 5 — Super Admin, Global User, Global Viewer, Regional User, Regional Viewer
Where does the business data live? The 4 SharePoint lists (Clients, Opportunities, Engagements, Companies) Unchanged — same 4 SharePoint lists. Only how they're reached is different
Written for the NeoEngage access-control redesign · the data itself never left SharePoint — only the path to it changed.
